# 租赁房源采集与数据质量分析：端到端执行方案

日期：2026-09-28。分支：`codex/data-collection-pilot`。

状态：设计基线 v4，执行中。范围为采集、清洗、指标计算及复验。指标口径变更须版本化，历史报告保留原口径。

## 1. 业务目标与边界

为 SafeScan 租赁管理助手筛选可用房源数据，建立可追溯的房型、报价和多模态资料集，支持房型检索、价格条件查询、布局与设施问答。通过试采比较有效信息、质量和成本，再决定扩采方向。

交付对象包括房源运营、数据分析及租赁助手服务。交付内容为经审核的数据版本、质量报告和来源扩展建议，分别服务于房源资料维护、来源投入决策和有来源依据的查询回答。

需要回答的决策问题：

1. 哪些数据源适合当前用途，权限是否明确？
2. 哪些房型具备可读户型图、匹配室内照片和口径清楚的报价？
3. 从候选到合格样本，主要损失在哪里，补采哪一类信息收益最大？
4. 每新增一条合格样本的请求量、人工审核时间及存储成本是多少？
5. 现有样本对普通住房、不同布局和城市的覆盖还有什么缺口？

非目标：不推断澳洲整体市场租金，不保证实时库存，不从营销照片判断具体房号当前安全状况，不采住户隐私，不把公开网页当作维修工单库。

## 3. 样本单位与入选标准

### 3.1 分析单位

- 学生公寓：`楼栋 + 来源房型ID` 为房型样本。不同租期是报价记录，不新增房型样本。
- 普通住房：优先使用来源房源ID表示一条挂牌；不同来源的相同住宅建立候选关联，不轻率合并。
- 房型与具体房号分表；同一房型下三个房号仍只有一套共享房型资料。
- 多个名称可能共用图纸或 VR。保留商业房型差异，同时统计唯一布局及媒体覆盖，不虚增视觉多样性。
- 比较来源时必须展示样本层级、采集时间与住房类别，避免房型样本和整套挂牌直接混算。

### 3.2 两道独立门槛

**质量合格**：

1. 有来源ID或稳定内部ID、来源URL、抓取时间、楼盘/房源名称、位置、房型/住房类型。
2. 至少一条报价具备金额、币种、周期、按人/按房间/按整套口径；租期条件明确，或来源明确未限制。来源未说明应填 `unknown`，不视为完整。
3. 至少一张人工确认可读、与该房型对应的户型图。分辨率只作为预警，不能替代可读性判断。
4. 至少两张去重后匹配该房型的室内照片；大堂、公共健身房和海报不计入。
5. 未解决的关键冲突为零，例如户型名称不同、面积口径不明却用于比较、图纸跨楼盘错配。

**用途获准**：记录并确认计划用途所需的访问、保存、衍生处理、第三方 AI 传输及展示权限。`unknown` 或 `pending` 不算获准。质量合格不抵消权限缺失。

视频和 VR 是加分项，不是硬门槛。二者分别统计；空播放器、网站通用频道、仅预约人工导览均不算房型视频。

## 4. 权限与采集准入

建立 `source_registry`，每个域名/来源记录：来源类型、官方入口、条款URL、robots检查时间、允许路径、用途、权限状态、许可证据位置、保留期限和展示范围。

权限状态：`unknown`、`pending`、`approved_for_scope`、`restricted`、`denied`。批准范围必须写明，不用一个布尔值代表所有用途。

- 网站公开、robots允许和非商业用途，都不自动等于素材自由再利用。
- 许可不明确时保留来源研究和缺口清单；不自动扩大下载或将既有样本发布到公开仓库、看板、模型训练集。
- 每轮重新检查相关规则。403、访问验证或明确禁止时停止，不通过代理轮换、伪装或登录绕过。
- 429 遵循服务端等待要求；若暂不实现恢复机制则停止该来源，记入日志。不能立即重试。
- 不访问住户账户、提交申请、预约或发送询盘。申请表中的个人资料不属于本项目目标数据。
- 内部分析、应用展示、对外导出分别校验用途权限；素材无展示许可时不显示原图。报表和导出只包含接收方有权访问的数据。
- 许可记录、联系人及凭证不提交公开 Git；到期或撤回时可按来源定位并处理原始文件、派生数据及缓存。

本方案是项目操作边界，不是法律意见。UniLodge 当前未确认开放授权，不能把来源候选视为已准入。

## 5. 分阶段执行与验收

| 阶段 | 输入与动作 | 产出 | 进入下一阶段的条件 |
|---|---|---|---|
| P0 业务定义 | 固定目标、样本粒度、指标和使用范围；审计已有文件 | 需求基线、基线统计、权限登记 | 指标口径无关键歧义；采集权限按范围判断 |
| P1 来源探索 | 检查首页、详情、租期报价、图纸和图库；建立候选清单 | 字段字典、来源地图、缺口表 | 确认至少一个来源的结构与可执行范围 |
| P2 小样本采集 | 在允许范围内获取固定目标，保存版本及失败原因 | raw、manifest、请求日志 | 有完整来源留痕，停止策略有效 |
| P3 清洗关联 | 类型转换、单位与价格口径标准化、去重、媒体归属审核 | staging、curated、隔离记录 | 数据契约检查通过；未确认项保留缺失 |
| P4 质量评估 | 全量审核首批小样本，计算漏斗和缺失原因 | 指标表、质检表、异常清单 | 所有指标可由明细复算，权限与质量分开 |
| P5 分析展示 | 来源对比、成本、覆盖偏差与样本追溯 | 三页看板、样本详情、一页决策报告 | 图表与明细一致，结论不超出样本范围 |
| P6 改进复测 | 选一个主要缺口修复，固定候选队列前后对比 | 改进记录、复测结果、扩采决策 | 改善可归因，未通过新增样本稀释失败 |
| P7 发布交付 | 冻结审核通过的数据及指标，校验使用范围，执行导入验证 | release清单、消费数据、验收记录 | 权限、数据契约和回滚方案通过审核 |

### 5.1 批次执行协议

运行顺序为：范围确认 -> 来源准入 -> 冻结候选 -> 采集 -> 标准化 -> 自动质检 -> 人工核验 -> 指标计算 -> 发布校验 -> 消费验证。已有数据允许从离线标准化开始，但不因此免除用途检查。

运行前明确 `run_id`、`cohort_id`、输入快照、配置版本、目标页面清单及停止条件。运行后产出成功、失败、未尝试及隔离明细，不静默缩小计划分母。保留请求限速、单次请求大小及固定页面范围等技术保护，避免无限遍历；这些限制不是财务或人员计划。

## 6. 首批样本与后续扩展

### 6.1 学生公寓试点

先核查 UniLodge Flagstaff 的 Standard Studio、Studio Terrace、4 Bedroom 三类，Queen 和 2 Bedroom 作为存在缺口的备选。先建 5 条候选档案，不承诺 5 条均合格。

候选清单必须记录发现路径、纳入/排除理由、当前缺失项。首次采集前冻结 `cohort_id`；后来新增候选使用新队列，不覆盖原分母。

先追求不同布局，而不是 Standard、Superior 等不同楼层/景观名称。房型图片若仅能确定属于楼栋，降级归属，不凭图片相似或文件名推定具体房号。

### 6.2 普通住房阶段

在学生公寓流程稳定且新来源通过准入后，再选获准使用的中介资料或正式接口：

| 类别 | 试点目标 | 新增核查项 |
|---|---|---|
| 普通 Apartment / Unit | 5-10 条挂牌 | 房号、整套价格、家具、车位、入住日期 |
| House | 5-10 条挂牌 | 土地/室内面积、庭院、附属建筑、多层图纸 |
| Townhouse / Duplex | 5-10 条挂牌 | 层数、共享结构、车库、室内外空间 |
| 合租房间，后续可选 | 独立批次 | 私有/共用空间、按人/房间报价、隐私 |

这是便利抽样的流程验证，不是代表性市场抽样。覆盖表按城市、来源、住房类型、卧室数、面积口径、家具及价格基础分层；零覆盖必须显示。不得只保留易获取、照片漂亮的样本而隐藏排除项。

## 7. 统一数据模型

所有实体均保留来源标识；原始值与标准化值并存。ID依据来源原生ID或稳定键生成，不使用价格、时间或展示顺序作为实体ID。

| 表 | 粒度与关键字段 |
|---|---|
| `source_registry` | 一来源：domain、terms_url、rights_status、approved_scope、checked_at |
| `collection_runs` | 一次运行：run_id、cohort_id、配置版本、代码版本、起止时间、状态 |
| `fetch_events` | 一次请求尝试：request_id、page_id、attempt、URL、HTTP状态、字节、耗时、重试/停止原因 |
| `page_snapshots` | 一内容版本：snapshot_id、URL、retrieved_at、hash、解析器版本、原文件位置 |
| `properties` | 一楼栋/住宅实体：来源ID、地址、城市、住房类别、品牌关系、产权未知标记 |
| `room_types` | 一来源房型：property_id、名称、人数、床型、厨房/卫浴、面积及面积口径 |
| `unit_listings` | 一具体挂牌：source_listing_id、property_id、可选room_type_id、原始房号、挂牌状态 |
| `offers` | 一房型或挂牌的一种租期报价快照：amount、currency、period、basis、from标记、租期、费用包含项 |
| `assets` | 一媒体内容/外链：kind、URL、hash、尺寸、local_path、许可、viewer_id、访问核验状态 |
| `asset_links` | 一关联：asset_id、实体ID、scope、证据、审核状态、审核者、时间 |
| `quality_checks` | 一次规则/人工检查：实体ID、rule_id、结果、严重度、证据、处理决定 |
| `candidate_samples` | 一候选：cohort_id、实体键、计划页面、纳入理由、评估状态和排除原因 |
| `work_logs` | 一段工作投入：run_id、任务类别、人工分钟、自动运行秒数、成本单位 |
| `issues` | 一异常：实体/批次ID、类别、严重度、状态、影响范围及修复版本 |
| `releases` | 一发布版本：release_id、输入快照、规则版本、校验结果、有效范围、撤回状态 |

实体到来源快照必须能追溯；相同媒体可通过关联表连接多个房型。重复运行不增加实体数量，报价或内容变化新增历史快照。

报价时间用时区明确的 ISO 8601；原始报价保留展示币种和周期。主看板只比较同币种、同计价基础、相近租期的报价。若另做周月换算，明确 `weekly * 52 / 12` 是分析换算值，不是合同扣款额。

`area_scope`：`bedroom`、`internal_unit`、`balcony`、`land`、`unknown`。来源未明确就填 unknown，不将卧室8㎡标成四卧公寓整套面积。

## 8. 清洗、媒体分层与异常处理

1. 解析结构化数据或明确的DOM区域，不用整页文本盲配房型；优先复用已有 Fetcher、哈希和日志逻辑。
2. 清理空白和类型但保留原文；缺失值用 null，另记 `missing_reason`：未提供、未解析、访问失败、不适用、存在冲突。
3. 对营销主图、报价、户型图分别取证；价格冲突保留各自时间和租期，不自行挑便宜值。
4. URL规范化不能删除影响房型/租期含义的参数。完全重复用内容hash，近似图片用感知哈希做候选，再人工确认。
5. 媒体分类：户型图、室内、公共设施、外观、宣传海报、视频、VR、未知。公共设施可另用，但不计入室内图门槛。
6. 房型归属证据按来源明确关联、标签匹配、人工核查记录；AI分类仅作建议，记录模型版本并人工确认关键关联。
7. 图片检查解码、宽高、可读性和图纸是否裁切；低清、示意图、通用展示图分别标注。
8. VR按模型ID去重，视频按媒体标识去重；链接存在、播放器可用和允许下载是不同状态。
9. 跨来源或新旧名称的房型只列候选映射，证据不足不合并。报错记录进入隔离表，不静默丢弃。

## 9. 指标字典

所有指标按 `run_id/cohort_id/source_id` 可下钻；展示 n/N、时间、样本层级与排除规则。分母为0显示 N/A，不显示0%。

| 指标 | 分子 / 分母 | 注意事项 |
|---|---|---|
| 请求成功率 | 预期成功响应尝试 / 全部请求尝试 | 重试计入请求数；403和429单列 |
| 页面获取率 | 最终取得有效内容的目标页面 / 计划目标页面 | 未尝试、规则拦截、网络失败分开 |
| 解析成功率 | 通过结构检查的页面 / 成功取得的目标内容页面 | 空结果不自动算成功；合法无报价单独标记 |
| 核心字段完整率 | 已填且语义明确的适用必填项 / 全部适用必填项 | `unknown`不算完整；不适用须有规则依据 |
| 质量合格率 | 质量合格的唯一候选样本 / 冻结队列唯一候选样本 | 同时展示已评估数；未评估不冒充失败 |
| 用途准入率 | 用途获准的质量合格样本 / 质量合格样本 | 不把权限不明当作数据质量差 |
| 各模态覆盖率 | 有该类可用且关联正确媒体的样本 / 已评估唯一候选样本 | 户型图、室内图、VR、视频分别算；说明室内图门槛 |
| 有效媒体占比 | 去重且符合本次用途的媒体数 / 获取的唯一媒体数 | 以内容而非文件下载次数统计；分类质量另报 |
| 完全重复率 | 原始媒体记录数减唯一内容数 / 原始媒体记录数 | 与实体重复率分开；近似重复另报 |
| 关联准确率 | 人工判定正确的关联数 / 已审核关联数 | 同时报告审核覆盖率；未决单列，不能排掉后美化 |
| 报价口径完整率 | 周期、币种、basis、条件均明确的报价 / 已提取报价 | 不以报价多增加房型合格率 |
| 单条合格样本成本 | 本轮全部采集清洗审核耗时 / 新增质量合格样本 | 自动等待与人工工时分开；另报用途获准样本成本 |

改进目标在首轮基线完成后确定，并在下一轮运行前冻结。硬性质量规则是：来源追溯完整、不可伪造缺失值、可用集合中关键错配为零。耗时来自工作日志，不能将整个批次墙钟时间等同于人工投入；未记录成本时显示未知，不估算为零。

## 10. 分析方法与决策规则

- 来源比较：展示样本量、合格率、缺口类别、审核成本、用途准入状态；便利样本只能支撑试点决策。
- 漏斗必须使用嵌套集合：唯一候选实体 -> 成功获取所需页面 -> 可解析 -> 质量合格 -> 用途获准。请求成功率是旁路工程指标，不能与实体数混成一个漏斗。
- 缺失字段热力图按来源和房型绘制；区分未提供与解析失败，分别决定换来源还是修解析器。
- 价格仅做可比子集描述，先展示范围和样本数；小样本不拟合市场模型，不将楼层价差解释为因果。
- 覆盖分析报告选样偏差，特别是学生公寓、单一城市、少数运营商和营销图片偏差。
- 复测先在同一原始快照上验证解析改进，再另做新抓取；区分代码改进与网站内容变化。
- 扩采条件：权限满足用途、首批人工核验完成、核心错配为零、主要缺失项有解释、离线重跑可复现。缺一项则修复或替换来源，而不是盲目加量。

## 11. 分析看板与决策交付

### 页面A：采集概览

候选到用途准入的实体漏斗、各阶段失败原因、运行时间/来源筛选、数据截至时间。避免把图片数量当成主成功指标。

### 页面B：质量与成本

字段缺失热力图、媒体分类占比、重复媒体分布、关联审核结果、每条新增合格样本的人工时间及网络成本。以 HOME 的混合图库作为数据清洗案例。

### 页面C：覆盖与业务价值

住房类型、城市、卧室数与布局覆盖；在可比子集显示租期报价。通过详情链接追溯房型、图纸、室内图片和来源证据。无展示许可时只展示获准使用的审核元数据。

### 11.1 操作与追溯

默认显示最近已发布版本；筛选项包括来源、采集批次、城市、住房类别、样本层级、质量状态和权限状态。每个指标提供口径说明、分子分母及明细入口，未发布批次须显著标记。

样本详情显示来源时间、房型与报价、媒体归属、缺失项和审核记录。报表导出携带 `release_id`、筛选条件、统计口径版本和导出时间。受限来源只允许导出获准字段，不通过下载功能绕过展示限制。

### 11.2 批次决策报告

每批交付一份报告，包含：范围及样本量、相对基线的变化、主要失败原因、质量与权限可用量、处理耗时、覆盖缺口、下一步行动。每项行动记录待解决问题、预期改变的指标与复验方法。

决策可选：维持来源、修复解析、补充附件、申请权限、缩小使用范围、暂停来源或扩展住房类别。所有结论须链接对应指标和样本证据；未验证原因作为假设列出。

## 12. 工程落地与可复现性

先沿用 `scripts/data_collection/` 的小型 Python 工具，分析优先使用 SQL/SQLite 与现有 Python 工具；不为几十条样本引入分布式采集。静态HTML或现有BI工具均可，先确保指标正确。

拟定产出结构，尚未创建完整实现：

```text
scripts/data_collection/              # 现有采集器；逐步补统一解析和质检
scripts/data_analysis/                # 已建：离线标准化、指标计算、报告及复验
docs/RENTAL-DATA-ANALYTICS-WORKFLOW.zh-CN.md
docs/data-analysis/                   # 已建：当前字典、指标口径、基线报告
data/collection-pilot/<run_id>/        # 已被忽略的本地数据根目录
  raw/                               # 经许可保存的原始内容
  staging/                           # 按来源解析的中间数据
  curated/                           # 统一模型与审核结果
  reports/                           # 指标明细、静态预览
  manifest.json                      # 配置、版本、hash和来源清单
```

每个运行记录代码提交SHA及dirty状态、解析配置版本、依赖版本、UTC抓取时间、文件hash。原始快照不可被清洗过程覆盖；重跑写新输出或验证幂等。公开仓库只保留代码、无敏感信息的报告和自制测试fixture，不提交版权状态未明的原始图文。

测试覆盖：价格周期/按人口径、面积作用域、空报价、名称变更、跨房型图库、重复VR、空视频模态、404/403/429策略、错误隔离、外键一致性、分母为零、指标明细与汇总一致。离线测试不访问网站。

可视化验收：桌面与窄屏无横向遮挡，图表分母和时间清楚，点击详情能到证据；对截图、数据及指标逐项核对。解析单元测试通过不等于浏览器展示已验证。

### 12.1 状态与交付契约

批次状态为 `planned -> running -> collected -> validated -> reviewed -> released`，失败进入 `failed`，部分成功进入 `partial`，等待人工决定进入 `on_hold`。只有审核通过的记录进入发布集合；部分失败批次可发布合格子集，但必须保留原队列及失败明细。

记录分别维护 `quality_status` 和 `rights_status`，保留来源采集时间，不合并成一个可用标记。消费视图按用途计算准入，不能通过修改质量状态绕过权限限制。

首期交付为版本化 JSON/CSV 与指标报告，字段定义包含类型、可空性、枚举、单位、主外键及来源证据。金额使用十进制定点数或最小货币单位，避免浮点误差。新增可选字段可兼容升级；字段删除、含义或单位变化需新契约版本及迁移说明。

学生公寓房型不能直接写成业务数据库中的具体可租物业；必须有真实挂牌映射才允许导入具体单元。没有库存证据时仅进入资料查询层，不创建租约、空房承诺或可预订状态。

### 12.2 发布与回滚

1. 生成候选release及manifest，冻结快照、解析器、质检规则、指标版本和核验记录。
2. 检查所有已发布记录的来源、外键、媒体hash、关键字段和用途权限；发布集合中不得存在未解决的关键错误。
3. 在隔离目录或暂存表导入；比对实体数、报价数、媒体关联数及指标汇总。
4. 执行业务查询验收：租期价格、按人/整套区别、面积作用域、户型媒体匹配、缺失信息提示和来源追溯。首批逐条验收，后续采用固定回归集并全量检查变更记录。
5. 原子切换当前版本指针或索引别名，保留上一合格版本；不在正在读取的数据集上逐条覆盖。
6. 导入失败或关键错配时回滚并记录受影响版本。权限撤回不能回滚到同样受限的旧版本，须先从所有消费视图和索引中移除受限数据。

发布验收同时检查数据和应用行为：缺报价不能显示为零元，过期报价必须提示时间，营销照片不得呈现为房屋检查证据，缺库存不得回答“当前可租”。未通过验收的版本保持未发布。

### 12.3 异常处理与复验

| 等级 | 例子 | 处理与恢复条件 |
|---|---|---|
| 阻断 | 权限撤回、个人信息误采、跨楼盘错配进入发布集 | 暂停受影响发布或使用；完成影响检查及复核后恢复 |
| 批次异常 | 页面结构变化、大量解析失败、触发请求限制 | 隔离受影响来源，保留最后合格版本及新鲜度提示；修复并离线回归 |
| 记录异常 | 个别低清图、缺价、无法匹配的房型名称 | 保留缺失原因，进入审核队列，不进入完整样本集合 |

异常流程：发现 -> 分级 -> 确定影响范围 -> 修复 -> 重算指标 -> 复核 -> 关闭。关闭记录必须包含原因、处理动作、验证证据及修复版本；不得只删除异常行。

每批结束后输出请求失败、解析数量变化、未知字段比例、价格异常变动、待核验关联、明确过期报价和权限到期清单。统计型阈值在基线确认后按来源配置；尚无基线时展示实际变化，不直接判为异常。

### 12.4 保留、删除与恢复

保留期限按来源和用途单独登记，未确定时不无限期积累原始内容。原始文件、媒体、派生表、向量索引及导出记录应有来源映射，支持撤回时定位。

授权到期或收到删除要求后，先停止相应消费，再按批准范围清理副本和缓存，记录处理结果；备份按相同权限和保留规则管理。仅保留允许保留的审计元数据，不在日志中复制已撤回内容。恢复备份前重新校验权限，避免重新引入已撤回的数据。

备份与恢复验收包括文件hash、实体数量、外键、release manifest及权限状态。凭证使用环境变量或受控凭证存储，不写入源码、请求URL日志或数据报告。

## 13. 维修数据的独立路线

先不将维修数据设为房源试点验收条件。真实工单通过物业/承包商授权脱敏导出获取，住户自己的记录不能代表内部完整调度过程。

未来所需字段：匿名工单ID、故障类别、优先级、报修/派单/到场/完工时间、状态历史、角色、费用及单位、经许可的附件。移除姓名、联系方式、门禁信息和可识别住户的照片，不把匿名ID直接连接公开房号。

没有真实数据时仅用标记 `synthetic=true` 的数据测试派单、状态和SLA计算，不报告真实业务效率提升，不给真实楼盘虚构维修历史。故障照片的安全识别评测另建有标注的合法数据集，营销照片不能替代。
